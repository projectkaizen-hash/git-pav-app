# Handoff prompt for a new agent workspace

Paste everything below the line into a new agent session (for example Google Antigravity) opened on a fresh clone of this repo. It is written to be self-contained, and it points at the files in `docs/completion/` instead of repeating them. Last updated 23 Oct 2026, after PR #13.

---

You are taking over the Pav Dental monorepo at https://github.com/projectkaizen-hash/git-pav-app (default branch `main`). Pav Dental is a UK private dental practice with clinics, mobile dental vans and video consultations. The repo is being finished in small, reviewable pull requests against a written plan. Your job is to set up a working local workspace, confirm every suite is green, then continue the plan from where it stopped. The owner is hisham.

## 1. Read these first, in this order

1. `AGENTS.md` (root): what each folder is, which folder a task belongs to, and the rules that apply everywhere. `CLAUDE.md` just points to it. The folder `AGENTS.md` files win for their own folder: read `admin-dashboard/AGENTS.md` before dashboard work. `website/AGENTS.md` is the contract for the Grok App Builder that generated the website, not for you; follow root `AGENTS.md` there.
2. `docs/completion/04-decisions.md`: the owner's 21 decisions. This is binding. Don't reopen a decision; if one needs to change, ask the owner and update the log in the same PR.
3. `docs/completion/03-plan.md`: change sets CS-01 to CS-47, with files, tests, acceptance criteria, dependencies and 🛑 markers. Linear project "Pav Dental: completion" in team ZIS mirrors it: CS-NN is issue ZIS-(NN+4).
4. `docs/completion/01-findings.md` and `02-gaps.md`: the finding IDs (for example BK-5, AU-1) that the change sets close.
5. `docs/completion/migrations.md`: the migration rules, and the one-off steps that must run after certain migrations are deployed.
6. `docs/completion/00-baseline.md`: the state of the repo before this work started.

Older top-level files (`MASTER_PLAN.md`, `REQUIREMENTS.md`, `AUDIT.md`, `architecture.md`, `code-review-2026-10-03.md`) are background. Where they disagree with `docs/completion/`, `docs/completion/` wins.

## 2. The four apps

Each folder has its own `package.json`, lockfile and deploy. There is no root package. Don't add a root workspace or move files between apps without asking.

| Folder | What | Stack | Node (CI) |
|---|---|---|---|
| `backend/` | The API. The only owner of patient and clinical data | Express, Prisma, Postgres 16 with PostGIS, Redis 7, Stripe, Daily, Sentry | 20 |
| `pavdental/` | Patient, clinician and van operator app | Expo SDK 57, Expo Router, Sentry | 20 |
| `admin-dashboard/` | One staff back office for the website and the app | Next.js 16 (Turbopack), shadcn/ui, biome, Sentry | 22 |
| `website/` | Public site and shop (www) | TanStack Start, Vite, better-auth. Generated by Grok App Builder | not in CI |

How they connect:
- The dashboard reaches app data only through the backend's `/api/admin/*` endpoints. It goes through an allowlisted proxy (`src/app/api/v1/admin/app/[...path]/route.ts` and `src/lib/pav-api.server.ts`), signed in as the staff member's own app account. Never give the dashboard a copy of app data or a connection to the backend database.
- The dashboard has its own database (PGlite locally, Neon in production) for website data: shop, blog, newsletter and forms.
- The app's schema lives only in `backend/prisma/`.

## 3. Set up the workspace

Clone the repo, then follow these steps for each app.

**Backend**
```bash
docker compose up -d postgres redis          # from repo root: PostGIS 16 and Redis 7 on 5432 and 6379
cd backend && npm ci && cp .env.example .env # then fill .env (see below)
npx prisma generate
echo "CREATE EXTENSION IF NOT EXISTS postgis;" | npx prisma db execute --stdin --url "$DATABASE_URL"
npx prisma migrate deploy
npm run prisma:seed                          # synthetic data; refuses to run against deployed databases
npm run hours:defaults                       # default clinic hours and rota (decision #12)
npm run dev                                  # API on :3000
```
- Local `.env`:
  - `DATABASE_URL=postgresql://pavdental:pavdental_secure_dev_password@localhost:5432/pavdental_db?schema=public`
  - `REDIS_URL=redis://localhost:6379`
  - `NODE_ENV=development`
  - Long random values for `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` and `AUDIT_IP_HMAC_SECRET`.
  - Stripe test keys only (`sk_test_`, `pk_test_`). Mock keys are refused outside development.
  - Leave Postmark, Twilio, Daily, KMS and Sentry blank or stubbed locally.
- Checks, which mirror `.github/workflows/ci.yml`:
  - Typecheck: `npx tsc --noEmit`
  - Unit tests: `DAILY_API_KEY=stub PORT=3000 npx jest --forceExit`
  - E2E: `NODE_OPTIONS="--import ./test/stubs/external-fetch.mjs" DAILY_API_KEY=stub PORT=3000 npm test`. This stubs postcodes.io and Daily.
  - Migration drift check: see the `prisma migrate diff ... --exit-code` step in `ci.yml`. It needs a `pav_shadow` database with PostGIS.
- The current baseline is 30 jest suites (209 tests) and 34 e2e tests, all passing. Jest suites that start a server use fixed ports 3015 to 3020. Give a new one 3021 or higher.

**App**
```bash
cd pavdental && npm ci && cp .env.example .env   # EXPO_PUBLIC_API_URL=http://localhost:3000 (Android emulator: http://10.0.2.2:3000)
npx expo start
```
- Checks: `npx tsc --noEmit` and `npm run test:all`.
- App tests are tsx scripts, not jest. Keep anything you test free of React Native imports. See `src/lib/error-scrub.ts` and its test.

**Dashboard**
```bash
cd admin-dashboard && npm ci && cp .env.example .env
# PAV_API_URL=http://localhost:3000, ADMIN_JWT_SECRET=<long random>, DATABASE_URL blank (PGlite)
npm run dev
```
- Sign in with the seeded local admin: `admin@pavdental.com` / `Password123!`. This is a local seed account only.
- Checks: `NEXT_TELEMETRY_DISABLED=1 npm run build` and `npx biome check <changed files>`.
- Use a real `npm ci`. A symlinked `node_modules` breaks Turbopack.

**Website**
- `package-lock.json` is out of sync with `package.json`, so `npm ci` fails. That is why the website has no CI job.
- Use `npm install` for now. `npm run dev` serves on :8080. Checks are `npm run typecheck` and `npm test`.
- Fixing the lockfile and adding a CI job is open work (section 7).

## 4. Ground rules (non-negotiable)

- **Health data.** No real patient data in fixtures, seeds, logs, screenshots, tickets or commits. Use synthetic data with `@example.test` emails. Treat any personal or health data reaching a log or an error report as a high-severity bug.
  - Log errors through `safeError` (`backend/src/lib/log-safety.ts`), never raw. Prisma errors can quote query values.
  - Don't put the clinical lead's name in fixtures or logs.
- **Stripe** is test mode only. Never write to a live account and never commit real keys. `.env*` files are git-ignored except `.env.example`.
- **Keep every suite green.** Never weaken, skip or delete a test to make it pass.
- **Stop and ask the owner before:**
  - destructive or irreversible migrations
  - any change to how payments are captured or refunded
  - deleting a feature
  - adding a paid third-party service
  - anything needing a legal, product or clinical decision (GDPR retention, NHS EPS scope, clinical wording)
- **Clinical wording** is a draft until the clinical lead (decision #11) reviews it. Use neutral, non-diagnostic wording and make no "24/7 AI" claims.
- **Small change sets.** One concern per PR. Commit titles start with the change set, for example `CS-09: ...`.
- **Migrations.** Follow `docs/completion/migrations.md`:
  - Additive only.
  - A header comment in each SQL file.
  - No backfills inside migrations; put them in batched scripts under `backend/scripts/`.
  - Foreign keys go on as `NOT VALID`.
  - Indexes on hot tables use `CREATE INDEX CONCURRENTLY` in their own migration.
  - Never run `prisma db push`. The CI drift check must stay clean.
- **Sentry** is wired into all three apps and is off until a DSN is set. Every event passes a scrubber: `backend/src/lib/error-tracking.ts`, `pavdental/src/lib/error-scrub.ts` and `admin-dashboard/src/lib/error-scrub.ts`. Don't add request bodies, users, breadcrumbs, replays or tracing.
- **Gotcha:** the backend's `standardResponse` middleware overwrites any `requestId` key in a 2xx JSON body with the trace id. Name such fields something else, for example `erasureRequestId`.

## 8. How to work

- Work through the change sets in order, one small PR each, branching from the latest `main`. Each PR needs:
  - What changed and why.
  - The tests added.
  - Any post-deploy step, which also goes into `migrations.md`.
  - Anything that needs the owner.
- Before opening a PR, run the checks for every folder you touched (section 3). CI runs backend, Docker, mobile and dashboard. Ask the owner to merge only when CI is green.
- When the owner decides something, add it to `04-decisions.md` in the same PR.
- When you are blocked on a 🛑 item, ask one clear question with a recommended answer, and carry on with unblocked change sets in the meantime.
- Start by setting up all four apps, running every check, and reporting the results (pass counts and anything red) before you change any code.
