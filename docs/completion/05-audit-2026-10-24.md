## 2. Fix before anyone else uses the test environment

Confirmed by reading the code. These aren't in any change set yet; the plan gains CS-48 to CS-50 for them.

1. **Any website shopper can use the dashboard's admin API, including Stripe refunds.**
   - `admin-dashboard/src/lib/auth/middleware.ts:28-32`: `requireAdmin` accepts any token `verifyToken` accepts and never checks a role or purpose. Shopper tokens from `/api/v1/auth/login` (`purpose: "auth"`) are signed with the same `ADMIN_JWT_SECRET`, and the website keeps them in `localStorage` and sends them as Bearer tokens.
   - `:34-36`: when `NODE_ENV` isn't `production`, every request is let through, signed in or not.
   - Several routes answer CORS with `WEBSITE_ORIGIN ?? "*"`.
   - Reachable: users, orders, discounts, products, and `orders/[id]/refund`. App data behind `/api/v1/admin/app/*` is safe; the backend needs a staff session.
2. **Any clinician can read any patient's video consultation summary.** `b/src/routes/video.ts:572-575` allows `role === "clinician"` with no assignment or care-team check.
3. **Demo passwords for the public test API are in the repo.** `docs/deploy/test-deployment-status.md:48,104` publishes the password for the seeded admin, clinician, operator and patient accounts on the Render deployment. The patient account needs only the password. The seed guard (`b/src/lib/seed-guard.ts`) checks the `NODE_ENV` of the machine running the seed, not the database it targets, so seeding the remote database from a laptop isn't stopped.
4. **A patient cancellation can be turned into a full refund.** `b/src/lib/late-deposit.ts:16-18` treats any `cancelled` appointment as a late payment. After cancelling a confirmed booking (and getting 0% or 50% back), calling `PATCH /api/booking/appointments/:id/confirm` refunds the rest. A retried `payment_intent.succeeded` webhook does the same.
5. **A webhook retry can refund a completed visit.** `b/src/routes/payments.ts:358-376` only treats `confirmed` as already applied. If Stripe retries after the visit moved on to `in_progress`, `completed` or `no_show`, the deposit is refunded and the patient is told their hold expired.
6. **Plaintext health data next to encrypted copies.**
   - `MessageThread.preview` keeps the first 160 characters of every message, and `subject` is plaintext (`b/src/routes/messages.ts:211,328`).
   - Staff notification emails carry the patient's subject and name, unescaped in HTML (`messages.ts:236-247,347-364`).
   - `AppointmentNote` notes, diagnosis and plan are plaintext and overwritten in place (`b/src/routes/booking.ts:854-869`).
7. **Video idempotency keys aren't scoped to the user.** `submit-triage:${key}` and `admit-patient:${key}` (`video.ts:259,423`) replay a cached result, including decrypted triage, before the ownership check, to anyone presenting the same key.
8. **Clients can store a forged "encrypted" envelope.** `b/src/lib/encryption.ts:370` stores client `triageData`/`accessDetails` as-is if it looks like an envelope. Decrypting it later throws, which breaks the clinician's schedule, and `/video/rooms` reads `admittedAt` from it, so a patient can skip the waiting room.
